# PR reviews service

Севрис назначения ревьюверов для Pull Request'ов для Avito Tech: Backend

## Getting started

Для начала работы необходимо иметь хотя бы `Docker`. В данном проекте использовался `Docker 28.5.1`

Файл `compose.yaml` расположен в `/deploy/compose`, файл переменных окружения находится в `/`

```sh
cp ./.env.dist ./.env
docker compose -f ./deploy/compose/compose.yaml up --force-recreate
```

Образ для docker compose можно собрать локально, для этого нужен git репозиторий с тэгом и docker. Сборку можно начать, вызвав команду `make docker`, если в системе установлен `make`, либо через `bash ./scripts/build-docker_review.sh`, если установлен `bash`

Также есть команда для сборки обычного исполняемого файла — `make native`

## Текущая реализация бизнес-логики и функционала

Можно создать `team` с набором `users` через эндпоинт `POST /team/add`, при этом изменить состав `team` после добавления нельзя, так как для этого надо указать в том же методе название команды, которое уже существует
Можно получить состав группы через эндпоинт `GET /team/get` с указанием `team_name`
Можно создать pull request через эндпоинт `POST /pullRequest/create`, который назначит случно выбранных членов команды на ревью
Можно перевсти pull request в состояние `MERGED` через эндпоинт `POST /pullRequest/merge` с указанием `pull_request_id`
Можно перенаначить ревьюера через эндпоинт `POST /pullRequest/reassign` с указаанием `old_user_id` и `pull_request_id`
Можно поменять статус активности пользователя

Нельзя получить список назначенных для пользователя `reviews`

### Проблемы реализации и вопросы к API и Техническому заданию

#### Обновление в `/team/add`

Вызов эндпоинта `/team/add` с новым именем команды и указанием id существующих пользователей с новым именем для этих пользователей, они будут ассоциированы с новой командой и их имя будет обновлено, однако вызов `/team/add` с именем, которое содержится в базе данных, приведет к ошибке `400: TEAM_EXISTS`, даже если задача - обновление состава команды или имени пользователя

Защита: не совсем понятно, что должен выполнять эндпоинт `/team/add` с точки зрения обновления данных, если существует группа `/users` с эндпоинтом `/users/setIsActive`
Возможные решения: добавление эндпоинтов `/users/edit` (или `/users/setIsAcive`, `/users/setName`), `/team/edit` для изменения информации о пользователе и группе соответственно.

Либо сделать обработку запроса в эндпоинте `/team/add` следующую: если состав команды `members` в запросе не изменился относительно текущего состава команды — возвращаем ошибку `400: TEAM_EXISTS`, иначе меняем состав пользователей и только его, считая, что имя пользователя не должно меняться, должно меняться только значение поля `isActive`

#### `MERGED` Pull Request без ревью

Можно произвести `merge` без назначенных ревьюеров, например, если пользователь один в команде.

Защита функционала: в ТЗ не сказано, что pull request без единого ревьюера не может быть быть в состоянии `MERGED`, также ошибка `NO_CANDIDATE` упоминается в контексте невозможности замены ревьюера, но не в контексте невозможности назначения

Возможное решение: запрет на принтие PR без ревьюеров

## Архитектура проекта и кода

Архитектура кода — слоистая. `handler` отвечает за обработку запросов по HTTP, `service` отвечает за бизнес-логику, `repository` отвечает за хранение и доступ к данным
Каждый уровень отвечает за свою зону ответственности, при необходимости происходит обращение к другому ответственному инстансу на том же уровне (`PRService` ->`UserService`)

Архитектура проекта вдохновлена [схемой golang-standards](https://github.com/golang-standards/project-layout)

### Сущности

**Пользователь (`User`)** — участник команды с уникальным идентификатором, именем и флагом активности `isActive`.

**Команда (`Team`)** — группа пользователей с уникальным именем.

**Pull Request (`PR`)** — сущность с идентификатором, названием, автором, статусом `OPEN|MERGED`и списком назначенных ревьюверов (до 2).

### Иерархия директорий и файлов в проекте

`/` — корень проекта, в данном случае сервиса назначения ревьюверов для Pull Request'ов

`/api/` — директория для описания API сервиса, содержащая `openapi.yaml`, прилагающийся к заданию, предоставляет интерфейс взаимодействия внешних сущностей с сервисом

`/build/` — директория для образов и артефактов сборки, в частности содержит `package` для описания образа `Docker`, `bin` для собранного нативно артефакта

`/cmd/` — команды разрабатываемого сервиса, в данном случае одна команда — запуск сервиса `review`

`/configs/` — открытая конфигурация проекта, которая должна содержать специфичные для окружения файлы, такие как `dev.yaml`, `prod.yaml`

`/deploy/` — директория, которая содержит конфигурации, необходимые для развертывания, в данном случае включает в себя `compose` — конфигурацию для `docker compose`

`/docs/` — директория для документации, в данном проекте — документации `swagger`

`/internal/` — директория пакетов, которые не должны использоваться внешними сущностями. Здесь сокрыта реализация бизнеслогики, работы с даннми, обработки запросов. Для доступа извне существует `/api` и `/pkg`

- `domain/` — место описания структу сущностей, DTO

- `http/` — транспортный уровень, в рамках проекта — `http`, содержит конфигурацию сервера в `server` и обработчики для каждого эндпоинта в `handlers`

- `middleware/` — содержит middlewares для транспортного уровня, в данном проекте здесь реализованы CORS

- `repo/` — уровень работы с данными, содержит функции для работы с реляционной базой данных для каждой сущности

- `service/` — уровень бизнес-логики, содержит функции для реализации функциональных требований к сервису

- `storage/` — содержит конфигурацию хранилища, в рамках данного проекта — `postgres`, предоставляя базу как `storage`, скрывая детали используемой базы данных

`/migrations/` — директория для хранения схемы миграций, в частности для `go-migrate`. Формат миграций (по два файла): `xxx-<name>.up|down.sql`

`/scripts/` — директория для скриптов, упрощающих процесс разработки, тестирования, сборки

- `build-docker_reivew.sh` — получает текущий тэг репозитория `git`, считает его как тэг репозитория OCI (например, dockerhub), собирает образ с помощью `buildx` с указанными параметрами, такими как имя репозитория, полученной версии.

- `build-native_reivew.sh` — получает текущий тэг репозитория `git`, использует его в ходе компиляции, компилиурет артефакт с указанием текущей версии и создает ссылку с тэгом `latest`

`/test/` — директория для e2e, интеграционных тестов

`/.env.dist` — пример файла переменных окружения с примером, содержащий необходимый их набор

`/.env` — файл переменных окружения для работы сервиса, содержащий чувствительную информацию

`/Makefile` — файл с командами проекта. При вводе `make` без аргументов отобразит доступные команды.

`/.golangci.yaml` — файл конфигурации линтера `golangci-ling` с большей частью значений по умолчанию
